### Round 1 — Phase 3 only — 2026-08-15 — fresh reviewer, repo access — **NOT READY**

**Round 0 — is this the right thing to build at all?** Yes, and asked once for this
episode. Phase 3 produces the observable §1 names and is the first phase to produce it in

The reviewer's method is worth recording because it produced three findings nothing
static could have: it built a throwaway crate **outside the repo** linking `llika-core`
by path, and ran a real single-station hill-climb against the shipped
`layout::cost::evaluate`. Every number below is from the shipped scorer.

Five blocking findings.

1. **OQ-1 was unresolved, the phase's own scope made it a precondition, and nothing in
   the repo could resolve it.** The 2011 paper is not in the tree. Closed as this spec's
   own operational decision on the Phase 2 precedent — exact overlap rejected, ordinary
   crossings left to `c1` — with §3's OQ-1 split into a closed implementation and an open
   reconciliation. The argument is the asymmetry the original OQ text already stated:
   only the hard reading can freeze the search, so the soft one is risk-dominant.
2. **No gate case exercised the crossing rejection, whichever way OQ-1 landed.** `c1 = 0`
   on the fixture at snap *and* after hill-climbing under every schedule tried, so the
   phase's headline decision would have shipped with zero coverage — OQ-5's tie-break
   failure one rule over. Fixed by a second fixture carrying a deliberate crossing.
3. **The octilinearity clause was unsatisfiable, as OQ-8 predicted.** Verified
   independently: all 17 corridors snap to {0°, 90°, 135°, 270°, 315°}, so the fraction
   is already 1.0. Resolved to non-decreasing, with the strict burden moved onto `t`. The
   reviewer also found the consequence that breaks the naive repair — Phase 2's golden
   file retires here, leaving no artifact of "the Phase 1 output" to measure against —
   which became gate assertion 1: `iterations = 0` reproduces the snap-only layout
   bit-for-bit.
4. **"Total cost at the final iteration is strictly lower than at the first" fails on a
   correct implementation.** The search reaches a fixed point *inside the first sweep* —
   `t` 37.166633 → 22.505867 during iteration 1, every later iteration a no-op, across
   `r_0` ∈ {1,2,3,4,5,8} × iterations ∈ {1…200} — so first and final are bit-identical.
   Reworded to before-versus-after the search, which passes with 39% to spare, and §2.4
   gained a paragraph stating that an early fixed point is correct behaviour.
5. **The order-flip rejection had no operational definition**, and the two readings are
   not close: rotation-invariant rejects 214 candidate moves, positional 981. Pinned
   rotation-invariant, on the grounds that "clockwise order" is a property of a cycle,
   reusing the direction ordering `c3` already implements. Its vacuity below degree 3 is
   now stated, and the gate test keyed to degree ≥ 3 so it cannot pass for the wrong
   reason.

Seven non-blocking findings, all accepted: the scope named two new files but none of the
integration points (`run_layout`, the two new `LayoutParams` fields, the module
declarations, and `tests/golden.rs` which must be *deleted* here or `cargo test` breaks
the moment the picture changes); no default iteration count or cooling law, though both

release a cell and is dropped inside `snap_to_grid`, so the search cannot reuse the type

this phase falsifies it; OQ-2 promised a visual gate that Phase 3's gate did not have;
the determinism clause did not say "across processes", where Phase 1 argued at length
that it must; and the observable claim "the first map that actually looks schematic"
overstates what the phase delivers, since OQ-8 established the Phase 1 map is already
fully octilinear.

**Grounding verified, nothing stale found:** `SchematicLayout`'s private fields are
reachable because `candidate.rs`/`hillclimb.rs` are child modules of `layout`; the cost
functions take a bare position slice and are callable per candidate exactly as needed;

### Round 2 — Phase 2 only — 2026-08-14 — same reviewer resumed — **READY**

Zero blocking findings. Converged in two rounds — the episode's second, well inside the
three-round cap.

Both blockers confirmed resolved **against the files rather than the changelog**, and the
reviewer re-derived rather than re-checked. On `c3` it enumerated all ten partitions of
360° into three multiples of 45° — costs 60, 120, 150, 210, 240, 240, 300, 300, 390, 480
degrees — establishing `135/135/90` as *the* minimum rather than merely a good case, and

and 1000, showing the exact zeros are not a unit-offset accident.

Three non-blocking findings, all folded in:

- **`π/3` must be spelled `FRAC_PI_3`, not `PI / 3.0`.** The two are different doubles, one
  ulp apart, and the computed floor is bit-exactly the former — so
  `assert_eq!(c3, PI / 3.0)`, the natural spelling given §2.3 derives the floor in π,
  fails on a correct implementation. The author re-measured before accepting: `false` for
  the equality, `3ff0c152382d7366` against `3ff0c152382d7365`. This is the same class of
  trap the `c5` paragraph had already been rewritten to pre-empt, one criterion over.
- **The `atan2` exactness is a libm property, not an IEEE guarantee** — recorded as a
  caveat naming the consequence: on another target it is a gate to re-key, not a bug.
- **`c4`'s `φ` read two ways** (interior angle vs turn angle); now named as the interior
  angle outright, though the following clause had already pinned it.

**Numbers re-measured this round** (by both reviewer and author, independently, in Rust on
this machine): all eight unit cell offsets give exactly zero under
`min(θ mod π/4, π/4 − θ mod π/4)`, three of them negative zero — exactly the `Δj < 0`
offsets; `PI == 4.0 * FRAC_PI_4`; `|sin 4θ|` gives 1.22e-16 at (1,1), which is what would
have failed the gate; the `c3` degree-3 floor is `FRAC_PI_3` to 0 ulps; `atan2(1,2)` is
26.5651°, `atan2(5,12)` is 22.6199°, and `tan 22.5° = 0.41421`, so 22.5° is not
constructible on an integer grid.

### Round 1 — Phase 2 only — 2026-08-14 — fresh reviewer, repo access — **NOT READY**

**Round 0 — is this the right thing to build at all?** Yes, and asked once for this
episode. Phase 2 produces **no** observable and the spec argues that explicitly rather
than assuming it: `c1`-`c5` are pure scoring functions with no path to the renderer, and
separating them from Phase 3 is what makes their expected values hand-computable on small
graphs instead of debuggable only through a picture. The argument holds. The "no
observable" risk the methodology warns about — such phases are the ones that get cut — is
answered here by a gate that is checkable *without* one: Phase 1's SVG must come out
byte-identical.

Two blocking findings.

1. **Four of the five criteria had no formula anywhere in the repo, and `c3` had neither a
   formula, a defined zero-set, nor a gate case.** §2.3 was a five-row table of one-line
   descriptions; the seed document carried the identical rows and no more; the code had
   none. The only source of real formulas is the 2011 paper, which the spec itself treats
   as an unconsulted dependency — OQ-1 is `needs-input` on a re-read of it — while Phase 2
   named no paper dependency at all. Resolved by pinning all five in a new §2.3
   subsection: the domain (integer grid cells, direction `atan2(Δj, Δi)`), a formula and a
   zero-set for each, and `c2`'s functional form with only OQ-6's target left open. The
   subsection is explicit that these are **this spec's** operational definitions rather
   than quotations from the paper, and that OQ-1's re-read is the occasion to reconcile
   them — a difference found then is a recorded change to these formulas, not a defect in
   the phase that shipped them.

   The reviewer's own reasoning was overstated on one point and the author corrected it
   while accepting the finding: it argued `c3`'s zero case was unsatisfiable because a
   degree-3 station can never reach even spacing. True at degree 3 — but a degree-4 cross
   reaches exactly zero. That made the fix sharper rather than weaker: the floor is now
   derived explicitly and the gate names both the degree-4 zero and the `π/3` degree-3
   floor. Round 2 then generalised it further.
2. **The gate's "`c5` exactly zero at each of the eight octilinear angles" was achievable
   under some natural formulations and not others, and the spec named none.** The reviewer
   measured it: deviation-from-nearest-multiple returns exact `0.0` at all eight over
   integer offsets, while `|sin 4θ|` — an equally faithful rendering of "four-gonality" —
   returns 1.22e-16 to 4.90e-16 at seven of them, failing the gate with correct code; and
   an edge built from `cos`/`sin` rather than an integer offset breaks exactness for every
   formulation. Resolved by specifying the formula and stating the eight test edges are
   unit cell offsets. Re-measuring it, the author found what the reviewer had not: three
   of the eight return **negative** zero, so the gate is an equality assertion and
   explicitly never `to_bits`.

Six non-blocking findings, all accepted. The most valuable was that **a derived `Default`
on `w1`-`w5` gives every weight `0.0`**, making `t ≡ 0` — a scorer that scores nothing,
which no per-criterion assertion would catch and which would then pass Phase 3's
cost-decrease gate. Also: the gate's "strictly positive at 22.5 degrees" is not
constructible on an integer grid at all (now offset `(2,1)`, 26.5651°); "byte-identical
before and after" named no baseline artifact, and the existing cross-process test compares
two runs of one build so cannot serve as the "before" (now a golden file committed at the
phase's base commit, retired at Phase 3); `c1`'s treatment of touching and collinear
degenerates was unstated; `c4`'s summation domain was ambiguous at `market`; and the
close-out omitted `rules/projection-grid.md`, which this phase falsifies.

The round also caught two stale prose claims, one of which reversed an author decision
made a few hours earlier: Phase 1's scope text still named `metro-cli` and
`metro-core/tests/fixtures/...`, which the author had deliberately left on the grounds
that a shipped phase's scope is an append-only record. The reviewer was right — a path
that no longer resolves is a broken fact, not a superseded decision — and §2.8's rename
note now says the correction applies document-wide and why.

**Grounding verified, nothing stale found:** every §2.8 module and symbol matches the tree

### Round 1 — Phase 1 only — 2026-08-14 — fresh reviewer, repo access — **NOT READY**

**Round 0 — is this the right thing to build at all?** Yes, and asked once for this
episode. Phase 1's defining property is that it produces a real, viewable SVG — a
genuine if degraded instance of the observable §1 names — before any layout
intelligence exists, and the spec argues explicitly for taking the whole slice
because every smaller cut of it produces nothing anyone can see. The observable is
the right one: a schematic-map generator exists to produce a map a person looks at,
and the candidates rejected when the project adopted this methodology (the
`SchematicLayout` coordinates, the parameter structs, the Tauri app) are respectively
invisible, invisible, and a delivery vehicle. Caveat recorded rather than waved:
Phase 1's output is grid-snapped with zero iterations, so it is a recognizable
network rather than a transit poster — the same artifact degraded, not a different
artifact.

Three blocking findings, all one cluster: **the numeric chain lat/lon → projected
plane → grid cell → SVG user unit was pinned nowhere in the spec or in either source
document**, and Phase 1 is the phase that must build all of it.

1. **Units of the projected plane and the value and home of `g` were unspecified.**
   The only numeric hint was `--grid-spacing 20` in §1 — a Phase 6 flag — and it is
   meaningless without units: at the sample coordinates' ~1.5 km spacing, `g = 20`
   in metres makes collision impossible and `g = 20` in degrees puts the whole
   network in one cell. Resolved by pinning all three coordinate systems with
   formulae, denominating the plane in metres, and giving `g` a home as
   `LayoutParams::grid_spacing: Option<f64>` whose default derives from the network.
2. **The gate clause "including the tie-broken pair" asserted a fixture property the
   fixture spec did not require.** Off-grid is not colliding — so the clause was
   either unsatisfiable or vacuous, and in the vacuous reading the OQ-3 tie-break
   would ship with zero coverage in the one phase that builds it. Resolved by
   requiring a colliding pair in OQ-5 and splitting the assertion into two halves.
3. **The tie-break had no resolution order, breaking §2.4's determinism claim.**
   OQ-3's proposal fixed the spiral's order but never said which of two colliding
   stations keeps the cell. Resolved by claim order = input `stations` array order,
   first claim wins, and by the general rule that input order is the iteration order
   everywhere it is observable — which names the per-process `HashMap` seeding hazard
   the reviewer predicted. **The author found a second instance the reviewer did
   not**: §2.4's "move to whichever lowers `t` most" had the same hole for equal-cost
   candidate cells, now broken by the same spiral order. Phase 1 gained a
   cross-process byte-stability assertion, since two in-process calls cannot catch a
   per-process hasher seed.

Nine non-blocking findings, all accepted — including that `geometry.rs`'s segment
intersection and angle math had no Phase 1 consumer (moved to Phase 2, where `c1`
and `c5` are their first tests), that §2.1's own JSON example would fail validation
(labelled a shape excerpt; a five-condition error contract added), that the edge
count named no literal, and that the SVG y-flip was unstated.

**The round's best catch was verification of OQ-5, not a finding against it.** The
reviewer opened the third document the sources point at and confirmed independently
that the 17-station fixture exists nowhere — no station ids at all in the agent
research file — and that the pointer chain dead-ends without looping back. It also
corrected OQ-5's description of that chain, which the spec had slightly wrong while
reaching the right conclusion.
